# Calistar

Privacy-first web and API analytics for Stellar ecosystem projects. Monorepo managed with [Turborepo](https://turborepo.dev) and pnpm workspaces.

## Layout

```text
apps/
  landing/     Landing page (Next.js 16), served at calistar.io
  docs/        Documentation (VitePress), served at calistar.io/docs
  gateway/     Ingestion gateway (TypeScript): the only public entry point, holds no data
packages/
  normalizer/  Path normalization: Stellar keys, UUIDs, hashes and IDs become placeholders
infra/
  compose/     Local stack: PostgreSQL, Umami, the OpenTelemetry Collector, the gateway, the reverse proxy
  collector/   Configuration of the OpenTelemetry Collector
examples/
  otel-node/   Example API instrumented with the OpenTelemetry SDK
  static-html/ Example site that loads the tracker
tests/
  e2e/         Stack tests, run against the local stack
  load/        Short load run (k6)
```

The gateway, the stack and the tests are a **proof of concept**. It runs on a developer machine and in CI. No Calistar service is hosted yet.

## Requirements

- Node.js 24 or later for the gateway and the tests (Node.js 22 is enough for the landing page and the documentation)
- pnpm 12 (`corepack enable` picks the version pinned in `package.json`)
- For the local stack: Docker with Compose, and about 4 GB of memory for the containers

## Commands

Run from the repository root:

```bash
pnpm install
pnpm dev          # start every app in development mode
pnpm build        # build every app
pnpm typecheck    # type-check every workspace
```

To run one workspace only, add a filter: `pnpm dev --filter @calistar/landing`.

## Run the proof of concept

Everything below runs on your machine. Images are pinned by digest, and every published port is bound to `127.0.0.1`.

### 1. Unit tests

No container needed. They cover the path normalizer, with a corpus of every Stellar key type generated by the Stellar SDK, and the gateway.

```bash
pnpm install
pnpm test
```

### 2. Start the stack

```bash
docker compose -f infra/compose/compose.yaml -f infra/compose/compose.test.yaml up -d --wait --build
```

This starts PostgreSQL, Umami 3.5.0, the OpenTelemetry Collector, the gateway, a reverse proxy, an example API and an example site. The second file publishes the gateway, Umami and PostgreSQL on `127.0.0.1` for the tests; without it only the reverse proxy is reachable.

| What | Where |
| --- | --- |
| Reverse proxy: ingestion, and Umami's read-only dashboard | `http://127.0.0.1:8080` |
| Example site | `http://127.0.0.1:8091` |
| Example API | `http://127.0.0.1:8090` |
| Gateway, directly (tests only) | `http://127.0.0.1:18080` |
| Umami, directly (tests only) | `http://127.0.0.1:13000` |
| PostgreSQL (tests only) | `127.0.0.1:15432` |

With Podman, use `podman compose` with the same arguments.

### 3. Stack tests

```bash
pnpm --filter @calistar/e2e exec playwright install chromium   # once
pnpm test:stack
```

They check, on the running stack:

- **API:** traces and logs sent to the endpoint leave nothing in either database or in the logs; a raw path is stored as a normalized route; a data point belongs to the token's tenant whatever the payload says; a cumulative stream is converted without double counting.
- **Web:** a page view from a real browser is counted by Umami; the visitor's address, the query string, the page title and the language are stored nowhere; the page sets no cookie and writes no device storage.
- **Single sign-on:** a provisioned view-only user opens its dashboard in Umami from a token, can read its website, cannot change it, and cannot read another tenant's.
- **Reverse proxy:** ingestion and the dashboard work through it; Umami's collection endpoint, its tracker script, its sign-in and every route that writes are not reachable.

### 4. Try it by hand

```bash
# An API request whose path holds a Stellar account
curl http://127.0.0.1:8090/accounts/GAUJMRUP23T5XGUUWR7UDPJFZQFB5YFCEVUPLD5XABUEHQT2V3VIJFMJ/payments

# A few seconds later: the stored row has the route /accounts/:account/payments
docker compose -f infra/compose/compose.yaml exec postgres \
  psql -U calistar -d calistar -c "select tenant_id, method, route, status_code, request_count from api_metric_1h"
```

### 5. Short load run

Needs [k6](https://k6.io).

```bash
k6 run tests/load/api-ingest.js && node tests/load/verify-counts.mjs
```

### 6. Stop

```bash
docker compose -f infra/compose/compose.yaml -f infra/compose/compose.test.yaml down -v
```

`-v` also deletes the database volume.

Local credentials are in `infra/compose/.env.example`. They are defaults for a developer machine and must not be reused anywhere reachable.

## How the apps share one domain

`apps/landing` and `apps/docs` are two Vercel projects. The landing owns `calistar.io` and proxies `/docs` to the docs project (its domain is read from `DOCS_ORIGIN`) with a rewrite in `apps/landing/next.config.ts`, so the documentation is read at `calistar.io/docs`. Setup steps are in [apps/docs/README.md](apps/docs/README.md).

The console does not exist yet and will not be hosted on Vercel. The landing redirects `/console` to it once `CONSOLE_URL` is set.
